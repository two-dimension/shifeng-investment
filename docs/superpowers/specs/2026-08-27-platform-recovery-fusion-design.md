# 石锋平台代码融合设计

## 一句话决定

以新电脑上的仓库作为最终仓库：AI 看板保留新版本，其他功能以 8 月 21 日前的旧仓库为准补回；全部功能恢复并验证后，再考虑迁移 Cloudflare。

## 目标

融合完成后只保留一个石锋平台主仓库。该仓库应同时具备：

- 新电脑上已经完成的 AI 看板；
- 旧仓库中的持仓、基金、新闻、日历、研究、MACD、TMT 两融、ETF、价格跟踪和量化功能；
- 旧电脑 Codex 任务生成的数据发布能力；
- 可在新电脑上运行的路径和配置，不再依赖 `/Users/rayw/...`；
- 完整、可回退的 Git 历史。

## 版本基准

| 范围 | 采用版本 | 说明 |
| --- | --- | --- |
| AI 看板前端、API、刷新脚本、数据契约和测试 | 新电脑当前仓库 | 不回退到旧版 AI 看板 |
| 除 AI 看板以外的平台功能 | 旧仓库实际工作树 | 采用旧仓库已提交和未提交的恢复内容，而不只采用旧 Git HEAD |
| 新电脑现有的非 AI 改动 | 先封存，默认不采用 | 只有明确修复新电脑兼容问题或属于 AI 看板依赖时才单独回补 |
| 历史 JSON、PDF、XLSX、PNG、量化和 TMT 数据 | 旧仓库与旧任务目录 | 与代码分开迁移，不放入 Git |

## 融合方法

### 1. 保护现有内容

- 为新电脑当前仓库建立融合前快照；
- 为旧仓库保存 Git 历史和工作树快照；
- 两个 Downloads 原目录在融合期间保持只读；
- 所有融合工作在新电脑仓库的独立分支或工作树完成。

### 2. 恢复非 AI 平台主体

先将旧仓库的非 AI 代码恢复到新电脑仓库，包括前端页面、服务端接口、脚本和测试。不得用整目录覆盖的方式处理共享文件。

以下共享入口必须逐项融合：

- `src/App.tsx`
- `src/components/Layout/MainLayout.tsx`
- `src/pages/index.ts`
- `server/index.js`
- `package.json` 与 `package-lock.json`
- `wrangler.toml`

这些文件的非 AI 行为以旧版为准，同时保留新版 AI 看板所需的路由、依赖和启动逻辑。

### 3. 叠加新版 AI 看板

在旧平台主体恢复后，保留新电脑版本的 AI 看板前端、服务端、数据刷新脚本和测试。若 AI 看板与旧平台共享工具或数据文件，应通过明确接口连接，不得用 AI 模块覆盖非 AI 功能。

### 4. 接入旧 Codex 任务

DRAM、NAND、业绩预告、业绩报告、巨潮资讯、新闻资讯和风险提示任务继续作为上游数据生产任务。融合时先保留其代码和历史，再将硬编码的旧电脑路径改成环境配置。

任务通过统一发布接口或结构化文件向平台交付结果，不再依赖某一台电脑的固定用户名和目录。

### 5. 迁移历史数据

代码恢复并能运行后，再迁移旧数据：

- 按数据类型和日期去重；
- 记录迁移前后的文件数、日期范围和校验和；
- PDF、Excel、图片和大规模量化数据保存在 Git 之外；
- `.env`、Token、SMTP 密钥和登录状态文件不得进入仓库；
- 无法确认的新旧数据都保留原件，不直接覆盖。

## 冲突规则

1. AI 看板冲突：采用新电脑版本。
2. 非 AI 功能冲突：采用旧仓库版本。
3. 共享入口冲突：保留旧版非 AI 行为，手工加入新版 AI 看板连接。
4. 数据冲突：不覆盖，按日期、来源和内容校验后决定。
5. 无法判断的冲突：停止该模块融合，保留双方版本并单独报告。

## 验收标准

融合完成必须满足：

- AI 看板保持新电脑当前功能；
- 持仓、基金、新闻、日历、研究、MACD、TMT 两融、ETF、价格跟踪和量化页面均可打开；
- 对应 API 能返回有效数据，不再因缺少模块或旧电脑路径而降级；
- 七套旧任务能在新电脑运行或成功向平台发布结果；
- 历史数据日期范围和数量经过核对；
- 前端构建、后端测试和主要页面/API 冒烟测试通过；
- 仓库中没有密钥、登录 Token、缓存、日志和大型运行产物；
- 融合过程可通过 Git 快照完整回退。

## 暂不处理

本阶段不部署 Cloudflare，也不重写成云端架构。Cloudflare 迁移只能在融合版本通过上述验收后开始。
